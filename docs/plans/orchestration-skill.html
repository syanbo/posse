Hive 编排技能计划

2026-10-16

目标与范围

把 hive task 的用法做成随 hive 版本更新的技能，在 hive 启动的 agent 里自动可用。正文借鉴 Orca orchestration 的结果约定、角色区分和收尾规则；常驻进程的协议不改，所以不用重启它，也不会断开终端。

要做：

  • 技能文件只放触发描述，正文由 hive 程序提供，和程序版本一致
  • 按会话注入给 hive 启动的 agent，不写用户的全局配置（和 hooks 的做法一致）
  • 改写正文：角色判断、任务说明的写法、拆分和等待的规则、逐个任务收尾汇报、失败后怎么处理
  • 补一个只在 CLI 里实现的 hive task retry，用原任务的说明重新派发

不做：Orca 的 Run / Task / Dispatch 三层模型、依赖图调度、心跳、远程放置。hive 是单机的，一个任务就对应一次尝试；有先后顺序的工作由协调方分批派发。

现状对照

hive 已经覆盖了日常编排的主干：派发、等待、问答、追加说明、关闭，以及 worktree 合并。差的是技能分发和正文里的约定，缺少的能力只有重试一项。

关键决策

事项决定理由
技能名和触发沿用 hive-tasks；描述写明"在 Hive 终端里（HIVE_TERMINAL_ID 已设）要派发、并行、监督其他 agent 时用"，并列出 claude、codex、grok用环境条件和 Orca 的技能分开
正文来源技能文件只写一句"先运行 hive task guide"，正文仍内嵌在程序里（internal/cli/task_guide.md）和 Orca 的做法一样，正文不会和程序版本脱节
Claude 注入hive 在 $HIVE_HOME/claude-plugin 生成一个只含 hive-tasks 技能的插件，启动和恢复会话时加 --plugin-dir；内容没变不重写已核实：插件里的技能能被自动触发，和 --settings 一起用正常
Codex、Grok 注入这两家没有按会话加载技能的办法，改为放一句指路（"要派发时先运行 hive task guide"）：Codex 用 -c developer_instructions=…，Grok 用 --rules已核实：Codex 的 -c skills.config 加不进外部技能，插件要装进全局缓存；指路方式两家都生效。-c 会整个替换 developer_instructions，用户的 config.toml 里设了它时不注入
worker 一侧worker 不需要技能：它的约定继续由 workerPrompt 在启动提示里给出，只补"可以改哪些文件"和"验收证据"两点worker 的启动提示本身就是权威说明，和 Orca 注入的前言是同一个作用
重试hive task retry <task> 先读原任务（show），再用同样的说明、agent 和工作区调用 task.start，标题加"（重试）"；只允许对 failed、exited、lost 的任务这样做不改常驻进程，也不改表结构
常驻进程不改协议改协议要重启常驻进程，会断开所有终端

正文改写要点

现在的正文共 41 行，改写后控制在 80 行以内：只写协调方当场要用的规则，细节交给 --help。

  1. 结果约定：每个任务都要有一个明确的结论，每个 worker 终端都要有去向（关闭或明确保留）。最后按任务向用户汇报：结论、证据、没解决的问题。
  2. 先判断角色：用户要求监督、等结果、并行汇总时，用 hive task；只是"交给另一个 agent 自己干"时，用 hive terminal create --agent 或 hive workspace create --agent --prompt，不建任务；有 HIVE_TASK_ID 说明自己是 worker，只按启动提示做事，不再当协调方。
  3. 任务说明必须能独立看懂，写清五项：目标（文件、设备、环境）、要得到的结果、约束和不许碰的东西、可以改哪些文件、证明完成的证据。
  4. 拆分：互相独立的任务全部派出后再等；有先后的分批派发；并行改代码一律用 --worktree；嵌套最多 3 层，到上限就自己做。
  5. 等待：task wait 超时或返回空只是检查点，不算失败；连续三次空等后用 task list / task show 看 worker 的屏幕；只有确证 worker 退出（exited、lost）才重试或关闭，看不到动静不算。
  6. 问答：worker 问的问题能自己判断的就直接 reply，判断不了才问用户；send 只追加说明，不能当作 worker 已经收到。
  7. 验收和收尾：拿到 done 后先核对报告里关键的结论，worktree 用 workspace diff 看改动，没问题再 merge；然后 task close，或者在给用户的汇报里说明保留哪个 worker、为什么保留。
  8. 失败：failed 先看总结和报告；exited 和 lost 先看 task show 里的屏幕结尾；确定要重来就用 task retry，不要再开一个说明相同、但没关联到原任务的新任务。

步骤与验收

  1. 核实注入方式（只读调研，不改代码）：分别用 Claude 的 --plugin-dir、Codex 的配置项、Grok 的参数各起一个临时会话，看 hive-tasks 能不能被列出、能不能被自动触发。
    • 验收：一张"agent × 注入方式 × 能否触发"的结论表，写回本计划
  2. 改写正文和 worker 提示：task_guide.md、--skill 的描述、workerPrompt。
    • 验收：hive task guide 的输出不超过 80 行；单测检查 workerPrompt 里有所有子命令的用法
  3. 按会话注入：在 internal/agent 里按第 1 步的结论加启动参数；插件目录由 Launcher 生成，内容不变时不重写。
    • 验收：单测检查生成的命令行和插件目录内容；端到端在 /tmp/hive-e2e/home 里新开一个 Claude 终端，问它有哪些技能，hive-tasks 要在列表里
  4. CLI：hive task retry；只有第 1 步核实到某个 agent 没法按会话注入时，才做 hive skill install。
    • 验收：单测覆盖 retry 复用原参数、拒绝重试还在进行的任务
  5. 场景演练：在 e2e 环境的一个小仓库里，让 Claude 当协调方，说"把这两件事派给 codex 和 grok 并行做完，用 worktree，合并前给我看结果"。
    • 验收：它加载了技能；派发时带 worktree；每个任务都等到结论；汇报逐任务写了证据；worker 都被关闭；故意让一个 worker 失败时，它会用 retry。同一个场景用 Codex 当协调方再跑一次
  6. 文档：更新 AGENTS.md 里多 agent 编排的约定。

每一步都要跑 go vet ./... && go test ./... && go tool mygo vet。新技能只有新开的 agent 终端才会带上，已经开着的终端要重开。

风险

风险应对
Codex 或 Grok 没有按会话加载技能的方式退回显式安装，由你执行；或者在这两家的协调方终端里，把正文放进启动提示（只限 hive 启动的 agent 终端）
插件里的技能不会被自动触发在描述里写清触发词；实在不行，就在 hive 启动的 Claude 终端里用 --append-system-prompt 加一句"需要派发时先运行 hive task guide"
和 Orca 的全局技能抢触发描述里写明 Hive 环境；最终是否移除 Orca 的技能由你决定（见下）
正文变长，占用上下文正文只在用到时才读，控制在 80 行以内
