# 会话历史

`posse history` 的索引和查询，以及界面的历史页。

- 会话历史（`posse history`）：
  - 只读各 agent 的会话目录，不写回（例外：会话标题，见 `agents.md` 的 `posse session title`；用户在历史页点"移到废纸篓"时，窗口确认后由目标常驻进程把会话文件或目录移到 macOS 废纸篓，只认目标用户各家会话目录里、路径和会话 ID 对得上的，见 `internal/daemon/history_trash.go`、`internal/history/trash.go` 和无界面适配 `internal/trash`）：claude `~/.claude/projects/*/*.jsonl` 和 `*/*/subagents/agent-*.jsonl`（子会话挂在父会话下，不另计一条）、codex `~/.codex/sessions` 和 `archived_sessions`（`rollout-*.jsonl`，以及 Codex 压过的 `rollout-*.jsonl.zst`；同一份两种都在时只索引明文，移到废纸篓时两种一起走；压过的文件在手机查看、上下文、技能和工具用量、图片视频扫描时整份解开再读（上限 1 GiB），文件没变不重复解开；标题取 `session_index.jsonl`）、cursor `~/.cursor/projects/*/agent-transcripts/*/*.jsonl` 和 `agent-transcripts/*/subagents/*.jsonl`（标题、目录、时间取 `~/.cursor/chats/*/<会话>/meta.json`）和没有转录文件的 IDE 对话（`~/Library/Application Support/Cursor/User/globalStorage/state.vscdb` 的 `composerData`，已有转录的不另收，带子会话标记的挂在父会话下；值为 NULL 的记录跳过；库戳变了也只重读 `composerData` 有变化的对话，解析规则升级时全部重读；气泡没读完时保留已索引的对话、不推进库戳；消息时间取气泡的 `createdAt`；手机按索引里的路径（`globalStorage/composer/<ID>`）直接从库里读；`cursor-agent --resume` 只认 CLI 会话，这类对话恢复时直接提示在 Cursor 里打开；库本身不移到废纸篓；历史页删除时只删这一条的 composerData、气泡、检查点等键，以及 composerHeaders 里同一 ID 的行）、grok `~/.grok/sessions/*/*/updates.jsonl`（没有这份或是空文件时才用 `chat_history.jsonl`；元数据取同目录 `summary.json`）。
  - 不入库的内容：agent 以用户身份注入的提醒、技能正文、AGENTS.md/环境信息、本地命令输出、压缩摘要；不是用户发起的会话（codex 里自动审批、`/review`、压缩、记忆整理和 `thread_source` 不是 user 的线程，grok 内部的目标规划）。用户发起的子会话挂在父会话下面：claude 子 agent、codex 的 `spawn_agent`、cursor CLI 与 IDE 的派生会话、grok 的 subagent、antigravity 的派生会话；父会话没被索引到（或不在这次筛选结果里）的仍单独列出。claude、cursor CLI 放在 `<会话>/subagents/` 下的子会话只认同一目录的那份父会话（cursor 同一个 ID 会出现在不同项目），那里没有时才认同 ID 的 IDE 对话；codex 子线程续写的段不带 `thread_spawn`，合并后只要任一段带父线程就仍挂在下面。列表顶层的先后、按天分组和 `Limit` 截断都按整棵树最近的更新时间（父会话旧、子会话新时跟子会话走），每行显示的仍是这条会话自己的时间；截掉的父会话连同子会话一起不出现。`posse history list` 的文本输出把子会话缩进打在父会话下面（`--json` 在 `children` 里）。桌面详情里，发起那次工具调用带「打开子会话」，父会话正文没写到子会话 ID 时从列表的子行打开。搜索结果仍是平的。工具调用和输出各截到 3072 个字符。思考过程记进详情、默认折成一行，不进全文搜索；每段截到 8192 个字符。没有正文的加密思考仍丢掉。新格式（`history_mode=paginated`）的 codex 会话读 `event_msg` 的 `item_completed`，另外读 `agent_reasoning`。用户在 Claude 工作时插进来的话不是 `type: user`，而是 `type: attachment` 的 `queued_command`（`origin.kind` 为 human、`commandMode` 为 prompt），历史和手机会话页都按用户消息收；同样是 queued_command 的后台任务通知、子 agent 回报不算。
  - 索引更新在子进程 `posse history index --progress` 里做（首次较慢，常驻进程内存不受影响），按文件的 size/mtime 增量读新增的完整行；offset 前的字节对不上就整份重读，文件消失就删除。没有后台常驻轮询：查询时索引超过 15 秒没更新才更新一次，最多等 3 秒，没做完先用已有结果。历史页开着时，窗口的状态轮询带上 `history`，常驻进程给这几家的会话目录各开一个监视（不给每个文件建快照），目录里有变化就马上做一次增量索引，索引仍在子进程里；做完后 `daemon.status` 的 `historyGen` 加一，窗口看到它变了就刷新列表和打开着的详情，页面关上就停。15 秒的刷新留着，监视漏了事件时还能跟上。Cursor 的 IDE 对话在 `state.vscdb`，这份库编辑器自己也在写，不单独监视，仍靠这 15 秒。旧窗口不带 `history`、旧常驻进程没有 `historyGen` 时，仍是查询时超过 15 秒才更新。桌面列表、搜索和详情允许查看身份调用：索引是目标端维护的派生数据，查询可触发增量更新，但不改写会话文件、不恢复终端、不取得控制权；主动强制索引不作为桌面查看接口开放。窗口在安排防抖和定时刷新时固定主机请求，成功和失败都在主线程应用前重新核对主机身份与查询序号；旧结果不能盖掉新搜索，重复打开同一会话也只采用最后一次详情请求。
  - 中文按子串匹配；英文末尾按前缀匹配；各词 AND，全都没有时退回 OR 并告诉调用方。排序：标题命中优先，再按 bm25（用户 4、助手 2、工具 1）和命中消息数。
  - grok 的正文是 `updates.jsonl`：连续的回复 chunk 合成一条（文件有变化时整份重读，避免半条回复留在索引里），每个用户 chunk 各算一条（同一 `promptIndex` 重发的提问在 `chat_history.jsonl` 里也是两条），连续的思考 chunk 合成一条、不进搜索，计划更新仍不入库，用户消息只留 `<user_query>`（没有这个标签、又带环境或规则壳的整段丢掉）；工具结果只认 `status` 为 completed / failed 的 `tool_call_update`（`content` 是数组，没有时用 `rawOutput`），进行中的那条只是工具说明。`chat_history.jsonl` 是压缩后的上下文快照，只在没有流水时索引；它不带时间，用户消息按 `prompt_index`、回复按开头文字、工具按调用 ID，对上同目录 `updates.jsonl`，对不上的沿用前一条的时间。手机对话读同一份：有非空流水就读它（规则同上，半行留到写完），没有才读快照；订阅的文件从一份换成另一份时整页替换。索引里的会话路径虽是流水，技能用量、工具统计和图片扫描仍读同目录的 `chat_history.jsonl`（`TranscriptPath`、`SkillStats` 换回快照）。
  - 解析前先按各家 parser 的 `wants` 粗筛（只认 `"type"` 等字段的值，冒号后有空格也能匹配），无关的行不做 JSON 解码。
  - Codex 新格式的会话会分成几个文件（会话 ID 相同），列表、搜索、`history show` 都合成一个，信息取最新一段、消息数相加、无标题时用第一段的提问，详情按段接起来、序号顺延，移到废纸篓时各段一起走。别家同一个 ID 的不同文件是不同会话，按会话文件区分。
  - 历史列表含索引里的全部会话（一行只有标题、目录和时间，侧栏只画看得到的行），默认按今天、昨天、最近 7 天、最近 30 天、1 个月前分组，分组条数加起来等于顶上的总会话数（子会话缩进挂在父会话下，不重复计入；统计和列表用同一套父子关系）；搜索仍只取最相关的 200 条。侧栏搜索框下的分段按钮可以换成按文件夹分组：会话归到目录所在的项目（项目和它的工作区、worktree 目录取最长匹配），不在任何项目里的用目录名，组按其中最近的会话排先后，选择记在 ui.json 的 `historyByFolder`。默认只展开第一组，点组标题展开收起（不记进 ui.json）；↑/↓ 在看得见的会话之间换选中，会话列表可聚焦。搜索键（默认 ⌘F）在侧栏收着时先展开侧栏再聚焦搜索框。
  - `history show` 的 `--tail`、`--tools` 对 `--json` 输出同样生效。
  - `history resume` 在会话目录所在的工作区（或 `--workspace` 指定的）里开终端，先 `cd` 回原目录（claude 按目录找会话）；同一会话已在 posse 终端里运行时直接返回那个终端，原目录已经不在时报错，设置里关掉的 agent 不恢复。没有对应工作区时报 not_found，界面会问要不要把目录加成项目。桌面恢复同时传会话文件路径，避免重复 ID 选到其他文件，并核对路径对应的会话 ID。恢复从点击时固定主机与控制身份，添加项目确认、添加后的再次恢复和打开终端都沿用它；切主机或控制身份变化后，旧确认和迟到结果失效，查看状态不启动恢复。
  - 详情在「复制恢复命令」旁边有「复制交接」：会话 ID、目录、`posse history show <id>`，给下一个 agent 粘贴。新开的 Claude、Codex（`SessionStart` 的 source 是 `startup` 或空，且这次启动不是恢复或压缩）从已有索引读该终端目录（含子目录）最近三条会话的标题和最后一句用户或助手的话，经 hook 的 `additionalContext` 交进去；不在 hook 里刷新索引，索引没有或查不到就不写。思考和工具调用不进这一句。不注入 Codex 的 `developer_instructions`，也不注入 Grok 的 `--rules`。
- 历史页列表顶上是总计（会话数、消息数、各 agent 会话数，取自 `history.list` 带回的 `status`）。本机详情里的路径点一下在访达中打开，远端路径只展示，不交给本机访达；移到废纸篓通过 `history.trash` 在目标执行，服务端接受时检查桌面控制身份；确认后先刷新索引取得当前分段，移动前直接读取源文件核对会话身份；若会话已恢复运行则拒绝。Cursor IDE 对话存在 state.vscdb，不能整库移到废纸篓，也不能在终端里继续。历史页的「删除」经确认后，在目标上只删这一条的记录，其它对话不动；Cursor 正占用数据库时拒绝，并提示先退出 Cursor。删完从索引去掉这条。运行状态检查和移动与 Posse 的历史/终端恢复串行，索引等待在锁外。删除后等旧索引轮次结束，再刷新索引；多文件会话部分移动失败也刷新并报告错误，不永久删除、不自动重做。"上下文 N%"是最后一次请求占的上下文，详情请求带 `context: true` 时由目标 daemon 从会话文件末尾往前读并返回（不需要用量的调用不读）；旧本机 daemon 缺字段时由窗口兼容读取，远端缺字段不读取本机文件：Codex 取 `token_count` 的 `last_token_usage` 和 `model_context_window`；Claude 取最后一条助手消息的 usage（输入和缓存相加，不含输出），文件里没有窗口大小，按模型推断（兼容提供商前缀和小数点版本号；Claude 5 起的 Opus、Sonnet 和带 `[1m]` 的是 100 万，其余已知系列 20 万，用量超过 20 万的算 100 万；认不出的模型不显示百分比）；Grok 只有每轮累计、Cursor 没有记录，不显示。

历史详情里的助手 Markdown 图片会按会话根目录加载：Cwd 是绝对路径时用 Cwd，否则用会话文件父目录，相对路径和 `/images/x.png` 都按该根解释；工具消息仍是纯文本。远端图片经详情请求捕获的目标资源读取，不读本机同路径，换会话、详情请求换代或换主机时关闭旧加载器并丢弃迟到结果。

Antigravity 会话位于 `~/.gemini/antigravity/brain`、`~/.gemini/antigravity-ide/brain` 和 `~/.gemini/antigravity-cli/brain` 下的 `<UUID>/.system_generated/logs/transcript.jsonl`。同一个 UUID 有多份时留修改时间最新的。标题、工作目录取 CLI 目录里 `cache/conversation_metadata.json` 的 summary，缓存缺失时保留正文索引、标题回退首句；缓存未提供 WorkspaceURIs 时目录仍未知。会话若尚未打开，从桌面或手机的历史页继续时可选工作区，CLI 可用 `--workspace`。SQLite `conversation_summaries.db` 只读查询父子关系（`conversation_summaries.parent_conversation_id` 和 `conversation_parents.parent_id`），派生会话挂在父会话下；缓存里的 Internal 标记仍排除内部会话。`sessions.parent` 这一列让 schemaVersion 升到 6，整份重建；只改某一家解析规则时仍用 parserVersions。

解析 USER_INPUT / PLANNER_RESPONSE / GENERIC：用户只取 `<USER_REQUEST>` 正文、剥离附加元数据与设置；工具参数解开嵌套 JSON。思考过程记进详情、默认折叠，不进搜索。带 truncated_fields 时按 step_index、type、created_at 核对后从同目录 transcript_full.jsonl 回读；缺失或身份不符则保留截断记录。手机对话增量读取使用同样规则。

Antigravity 上下文取最近有效 PLANNER_RESPONSE 的 input_tokens + cache_read_tokens，缺少可核实的窗口容量，仅显示已用 token。媒体读取 media[].uri 的本地文件，以及 brain/<UUID> 下 .user_uploaded 和产物（目录扫描不跟随软链接）。移到废纸篓前核对 UUID、固定目录层级与软链接边界，移动整个 brain/<UUID>；这是日志和产物的删除，Antigravity 的 conversations/*.db、摘要缓存与搜索数据库保留，原生恢复可能重建日志。
